今天结论

重构不是重写 重构是在功能基本不变的前提下，让代码更清楚、更少重复、更容易维护。
自动文档也要整理 tags、summary、description 会直接改善 /docs 的可读性。
交付物不只有代码 README.md 说明怎么运行，api-docs.md 说明接口怎么调用。
一句话记法：能跑是第一步；Day 7 的重点是让未来的自己和别人都能看懂、测懂、接着改。

FastAPI 文档整理

Day 7 先定义接口分组，再传给 FastAPI。

tags_metadata = [
    {
        "name": "health",
        "description": "检查服务是否正常运行。",
    },
    {
        "name": "todos",
        "description": "内存版 Todo 的新增、查询、修改和删除接口。",
    },
    {
        "name": "review",
        "description": "第一周小项目的复盘辅助接口。",
    },
]

app = FastAPI(
    title="FastAPI Day 7 Todo API",
    description="第一周复盘项目：把 Day 6 的内存版 Todo CRUD 整理成更清楚的代码和接口文档。",
    version="1.0.0",
    openapi_tags=tags_metadata,
)
这些配置不是给 Python 运行逻辑看的，而是给 API 使用者看的。文档越清楚，沟通成本越低。

抽出 TodoBase

TodoCreate 和 TodoReplace 都需要 title、description、priority，所以 Day 7 把公共字段放进 TodoBase。

class TodoBase(BaseModel):
    title: Annotated[
        str,
        Field(min_length=1, max_length=80, description="待办标题"),
    ]
    description: Annotated[
        Optional[str],
        Field(max_length=300, description="待办说明"),
    ] = None
    priority: Annotated[
        int,
        Field(ge=1, le=5, description="优先级，1 最低，5 最高"),
    ] = 3


class TodoCreate(TodoBase):
    ...


class TodoReplace(TodoBase):
    completed: bool = False
这个抽取很小，但方向很对：重复字段越集中，后面调整字段规则时越不容易漏改。

TodoPatch 为什么单独写

TodoPatch 没有继承 TodoBase，因为局部更新里的字段都应该是可选的。

class TodoPatch(BaseModel):
    title: Optional[str] = None
    description: Optional[str] = None
    priority: Optional[int] = None
    completed: Optional[bool] = None
如果 TodoPatch 继承 TodoBase，那 title 会变成必填。这样只传 {"completed": true} 的局部更新就会失败。

健康检查和统计接口

GET /health 返回服务状态、服务名和版本号。以后学部署时，健康检查会很常见。
GET /todos/stats 返回总数、完成数、未完成数、高优先级数量，用来复盘当前内存数据。 
def build_todo_stats() -> TodoStats:
    total = len(todos)
    completed_count = sum(
        1
        for todo in todos.values()
        if todo["completed"]
    )
    high_priority_count = sum(
        1
        for todo in todos.values()
        if todo["priority"] >= 4
    )

    return TodoStats(
        total=total,
        completed=completed_count,
        active=total - completed_count,
        high_priority=high_priority_count,
    )
这里也体现了重构思路：接口函数处理 HTTP，统计逻辑放到普通 Python 函数里。

README 和接口文档

文件 解决的问题 应该包含什么
README.md 别人第一次打开项目时，怎么理解和运行它。 项目介绍、运行方式、接口列表、测试顺序、当前限制。
api-docs.md 别人调用接口时，需要知道请求和响应怎么写。 方法、路径、参数、请求体、响应示例、状态码。
/docs 是交互式文档，api-docs.md 是可阅读、可沉淀的接口说明。两者可以互补。

验收顺序

  1. 启动服务：uvicorn my_day07.main:app --reload
  2. 打开文档：http://127.0.0.1:8000/docs
  3. 执行 GET /health，确认服务正常。
  4. 执行 GET /todos，查看 Todo 列表。
  5. 执行 GET /todos/stats，查看统计信息。
  6. 执行 POST /todos，新增 Todo。
  7. 执行 PATCH /todos/{todo_id}，只修改 completed。
  8. 执行 PUT /todos/{todo_id}，整体替换 Todo。
  9. 执行 DELETE /todos/{todo_id}，删除 Todo。
  10. 再次查询被删除的 Todo，确认返回 404。
