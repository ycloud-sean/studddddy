Day 6 FastAPI 学习笔记

今天把路径参数、查询参数、请求体、响应模型、状态码和错误处理串起来，完成一个内存版 Todo CRUD。

主题：内存版 CRUD 资源：Todo 代码：my_day06/main.py 接口：GET、POST、PUT、PATCH、DELETE

今天结论

CRUD 是接口设计习惯 POST 新增，GET 查询，PUT/PATCH 更新，DELETE 删除。
模型要按场景拆开 TodoCreate、TodoUpdate、TodoPatch、TodoRead 的职责不同。
PATCH 只改传入字段 model_dump(exclude_unset=True) 可以避免没传的字段被默认值覆盖。
一句话记法：内存字典负责暂存数据，Pydantic 模型负责输入输出结构，HTTP 方法负责表达你要做哪种操作。

CRUD 对照表

操作 含义 HTTP 方法 本节接口
Create 新增资源 POST POST /todos
Read 查询资源 GET GET /todos、GET /todos/{todo_id}
Update 修改资源 PUT、PATCH PUT /todos/{todo_id}、PATCH /todos/{todo_id}
Delete 删除资源 DELETE DELETE /todos/{todo_id}

todos = {

        "priority": 3,
        "completed": False,
        "internal_note": "学习数据，不返回给客户端",
    }
}
内存版数据适合练接口，但应用重启后，运行期间新增、修改、删除的数据都会丢失。真正项目后面要换成数据库。

模型拆分

模型 使用场景 关键字段 为什么这样设计
TodoCreate 新增 Todo title、description、priority 客户端不传 id，新 Todo 默认未完成。
TodoUpdate 整体替换 Todo 完整可写字段 PUT 更像用一份新对象替换旧对象。
TodoPatch 局部修改 Todo 所有字段都可选 PATCH 只修改客户端传来的字段。
TodoRead 返回给客户端 id、title、priority、completed 响应模型只暴露客户端应该看到的数据。
模型拆开以后，接口意图会更清楚：请求模型描述“客户端要给我什么”，响应模型描述“我要返回给客户端什么”。

查询列表

GET /todos 支持按标题、完成状态、最低优先级和数量限制来筛选。

@app.get("/todos", response_model=TodoListResponse)
async def list_todos(
    q: Optional[str] = None,
    completed: Optional[bool] = None,
    min_priority: int = 1,
    limit: int = 50,
):
    result = list(todos.values())

    if completed is not None:
        result = [
            todo
            for todo in result
            if todo["completed"] == completed
        ]
这里要写 completed is not None，不能写 if completed。因为 completed=false 也是有效筛选条件。

404 复用函数

详情、更新、删除都会遇到“资源不存在”的情况，所以抽出 get_todo_or_404。

def get_todo_or_404(todo_id: int) -> dict:
    todo = todos.get(todo_id)

    if todo is None:
        raise HTTPException(status_code=404, detail="Todo 不存在")

    return todo
这个函数让接口代码更干净：先拿到 Todo，拿不到就直接返回 404。

新增 Todo

POST /todos 会生成新的 id，把请求体转成字典，再存进内存。

@app.post(
    "/todos",
    response_model=TodoCreateResponse,
    status_code=status.HTTP_201_CREATED,
)
async def create_todo(todo: TodoCreate):
    todo_id = max(todos.keys(), default=0) + 1
    new_todo = {
        "id": todo_id,
        **todo.model_dump(),
        "completed": False,
    }

    todos[todo_id] = new_todo
201 Created 表示资源创建成功，比普通的 200 OK 更准确。

PUT 和 PATCH

PUT：整体替换 适合客户端提交一份完整对象。没传的字段会按模型默认值处理，例如 description 可能变成 null。
PATCH：局部修改 适合只改一个或几个字段。比如只传 {"completed": true} 来标记完成。 
stored_todo = get_todo_or_404(todo_id)
update_data = todo.model_dump(exclude_unset=True)
updated_todo = {
    **stored_todo,
    **update_data,
}
todos[todo_id] = updated_todo

exclude_unset=True 的区别

本节最容易踩坑的是 PATCH 里的这一行：

update_data = todo.model_dump(exclude_unset=True)

如果请求体只传：

{
  "completed": true
}

加了 exclude_unset=True，导出的数据只有真正传入的字段：

{"completed": True}

如果不写 exclude_unset=True，TodoPatch 里没传的字段也会带着默认值一起导出：

{
    "title": None,
    "description": None,
    "priority": None,
    "completed": True
}
不写 exclude_unset=True 时，合并字典会把原来的 title 和 priority 覆盖成 None，局部更新就变成了误覆盖。
exclude_unset=True 和 exclude_none=True 不一样。前者是不导出“没传”的字段；如果客户端明确传了 {"description": null}，仍然可以保留这个字段，用来主动清空说明。

删除 Todo

DELETE /todos/{todo_id} 成功后返回 204 No Content。

@app.delete(
    "/todos/{todo_id}",
    status_code=status.HTTP_204_NO_CONTENT,
)
async def delete_todo(todo_id: int):
    get_todo_or_404(todo_id)
    del todos[todo_id]

    return Response(status_code=status.HTTP_204_NO_CONTENT)
204 的意思是成功但没有响应体。如果想返回 {"message": "删除成功"}，就不要继续用 204。

响应模型过滤字段

内存数据里有 internal_note，但 TodoRead 没有这个字段。

class TodoRead(BaseModel):
    id: int
    title: str
    description: Optional[str] = None
    priority: int
    completed: bool
因为接口设置了 response_model，FastAPI 会按照响应模型过滤返回值，内部备注不会暴露给客户端。

建议测试顺序

  1. 启动服务：uvicorn my_day06.main:app --reload
  2. 打开文档：http://127.0.0.1:8000/docs
  3. 运行 GET /todos 查看初始数据。
  4. 运行 POST /todos 新增一条 Todo。
  5. 运行 PATCH /todos/{todo_id}，只把 completed 改成 true。
  6. 运行 PUT /todos/{todo_id}，观察整体替换的效果。
  7. 运行 DELETE /todos/{todo_id}，确认返回 204。
  8. 再次查询被删除的 Todo，确认返回 404。
